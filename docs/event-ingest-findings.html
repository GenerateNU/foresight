What cleaning does, on real records

  • Merges duplicates. PredictHQ often lists one event several times. Records with the same normalized title, city and local date become one event.
  • Normalizes titles by dropping tour names, "(Touring)", "presented by…" and "feat." so two sources can match.
  • Converts to local dates. An 8 pm show is stored on that night, not on the next day in UTC.
  • Fixes coordinates. PredictHQ sends [longitude, latitude], so they are swapped and range-checked.
  • Validates. Records missing an id, title or date, ending before they start, or with impossible coordinates are logged and counted as rejected, and the run continues.
  • Keeps cancellations. Deleted events stay in the table marked deleted, so the model knows to drop them.

Finding: re-runs were deleting live events

Found by the re-run test, fixed the same night

Re-running the Dublin query a minute after the first run reported 238 updated instead of 0, and 20 live events switched to deleted. The cleaner correctly ignored a deleted duplicate listing on the first run. On later runs it treated that listing as the event's own record and applied its deletion. Live duplicates that differed slightly, such as attendance 210 and 211, also overwrote each other on every run.

Fix: each sighting now stores its own status. Every listing of an event is ranked the same way: structured source first, then live over deleted, then the latest revision. Only the top-ranked listing sets the event's values, so every run picks the same one.

What it means for the pricing model

The cleaned events become one model feature: expected_attendance, the total expected attendance near the hotel each night. Same-night events are added together, a multi-day event's attendance is split over its nights, deleted events are excluded, and provisional events count by their confidence. Open questions and next steps

  • API, not scraping. Events come from PredictHQ's API, which gives structured dates, venues and attendance, instead of from scraped web pages. AskNews (news articles) is the planned second source and plugs into the same cleaning.
  • Network retries. One Boston run failed on a PredictHQ read timeout. The ingest should retry before giving up.
  • Very large events. The marathon's 349,723 includes spectators. The model learned from mock nights topping out near 40,000, so it can't price beyond that range. It needs a cap or a log scale once trained on real data.
  • Multi-day attendance. This is assumed to be a total and split evenly across nights. Confirm against PredictHQ's documentation.
  • Missing attendance. 207 events across both cities have no estimate and currently add nothing. PredictHQ's 0–100 rank could fill the gap.
  • Real training data. Load hotel history into daily_performance and train on it with the same attendance feature.
